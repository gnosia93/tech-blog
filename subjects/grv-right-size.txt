핵심 앵글: "Graviton 전환 = 리사이징 기회"

가장 강력한 훅은 Graviton의 1 vCPU = 1 물리 코어(SMT 없음) 라는 점입니다. x86은 1 vCPU = 1 하이퍼스레드죠. 그래서 m5.4xlarge → m7g.4xlarge 같은 1:1 lift-and-shift는 대부분 과다 프로비저닝입니다. 실제로는 vCPU 수를 줄일 여지가 있고, 여기서 "전환 30% + 리사이징 20~30%"의 복리 절감이 나옵니다. 대부분의 Graviton 컨텐츠가 전환만 다루고 리사이징을 놓치기 때문에 차별점이 됩니다.

❯ ec2 인스턴스 sp 가 뭐야?

EC2 Instance Savings Plans

"특정 리전의 특정 인스턴스 패밀리를 1년 또는 3년간 시간당 $X씩 쓰겠다"고 약정하고 할인받는 요금 모델입니다. 예: us-east-1의 M5 패밀리에 시간당 $10 약정.

약정 단위가 인스턴스 개수가 아니라 시간당 금액($/hour) 이라는 점이 RI와 다릅니다. 약정액만큼은 할인가로 청구되고, 초과 사용분은 온디맨드 요금이 붙습니다.

유연한 것 / 고정된 것

바꿔도 계속 적용됨 (패밀리+리전 내에서)
- 인스턴스 사이즈 — m5.large ↔ m5.24xlarge
- OS — Linux ↔ Windows
- 테넌시, AZ

바꾸면 적용 안 됨
- 인스턴스 패밀리 — m5 → m6i도, m6i → m7g도 다른 패밀리로 취급
- 리전

3종 비교

┌─────────────────┬──────────────┬───────────────────────────────────────┬──────────────────────────┐
│                 │ 할인폭(최대) │                유연성                 │        커버 범위         │
├─────────────────┼──────────────┼───────────────────────────────────────┼──────────────────────────┤
│ EC2 Instance SP │ ~72%         │ 패밀리+리전 고정, 사이즈/OS만 유연    │ EC2만                    │
├─────────────────┼──────────────┼───────────────────────────────────────┼──────────────────────────┤
│ Compute SP      │ ~66%         │ 패밀리·리전·아키텍처 전부 자유        │ EC2 + Fargate + Lambda   │
├─────────────────┼──────────────┼───────────────────────────────────────┼──────────────────────────┤
│ Standard RI     │ ~72%         │ 패밀리+리전 고정 (조건부 사이즈 유연) │ EC2 (+ 일부 서비스별 RI) │
└─────────────────┴──────────────┴───────────────────────────────────────┴──────────────────────────┘

즉 EC2 Instance SP는 할인폭을 최대로 가져가는 대신 유연성을 포기하는 선택입니다. 여러 SP를 보유하면 AWS가 할인율 높은 쪽부터 자동 적용합니다.

Graviton 전환에서 문제가 되는 이유

앞서 언급한 "커밋 좌초"가 여기서 발생합니다. m6i 패밀리에 3년 EC2 Instance SP를 걸어둔 상태에서 m7g로 전환하면:

- Graviton 인스턴스는 온디맨드 요금으로 청구 (SP 적용 안 됨)
- 동시에 안 쓰는 m6i 약정액은 계속 청구

결과적으로 이중 지불이 되어, Graviton으로 30% 절감했다는 계산이 실제 청구서에서는 오히려 증가로 나타납니다.

대응 순서
1. 전환 대상 워크로드의 커버리지가 EC2 Instance SP인지 Compute SP인지 먼저 확인 (Cost Explorer의 Savings Plans 유틸리제이션/커버리지 리포트)
2. EC2 Instance SP라면 → 만기 시점에 맞춰 전환 일정 조정, 또는 만기 후 Compute SP로 갈아타기
3. 약정을 계단식으로(ladder) 쪼개서 갱신 → 아키텍처 전환 유연성 확보

Graviton 전환을 계획 중이라면 할인폭 6%p를 포기하고 Compute SP를 쓰는 게 대체로 유리합니다. 6%p 차이보다 전환으로 얻는 절감이 크기 때문입니다.

▎ 할인율 수치는 AWS 공식 기준의 "최대값"이고 인스턴스 타입·기간·선결제 옵션에 따라 실제값이 달라집니다. 컨텐츠에 넣을 때는 실제 대상 패밀리로 계산기 값을 뽑아 쓰는 걸 권합니다.

❯ 워크로드 진단에 대해서 좀더 자세히 설명해 줄래?

워크로드 진단은 두 개의 독립적인 축을 동시에 보는 작업입니다. 하나만 봐서는 판단이 안 됩니다.

- 축 A — arm64 호환성: 애초에 Graviton에서 돌아가는가? (기술적 가능성)
- 축 B — 리사이징 여지: 지금 과다 프로비저닝인가? (사용률)

arm64 준비가 됐어도 이미 딱 맞게 사이징된 워크로드가 있고, 과다 프로비저닝이지만 벤더 에이전트 때문에 arm64가 막힌 워크로드가 있습니다. 두 축을 곱해야 우선순위가 나옵니다.

2단계: 어떤 지표를 볼 것인가 (여기가 컨텐츠의 진짜 알맹이)

평균 CPU는 쓰지 마세요. 대신:

- p95/p99 CPU — 리사이징은 피크를 견디는지의 문제입니다
- 실사용 메모리(RSS 워킹셋) vs 할당 메모리 — JVM은 힙 설정 때문에 항상 꽉 차 보입니다. GC 로그나 힙 사용률을 따로 봐야 실제 여지가 보입니다
- 네트워크 대역폭·PPS — ⚠️ 가장 자주 빠뜨리는 항목. 인스턴스 baseline 대역폭은 사이즈에 비례합니다. c6i.8xlarge → c6i.2xlarge는 CPU에 여유가 있어도 네트워크에서 먼저 터집니다. 작은 사이즈는 burst 크레딧에 의존하므로 지속 트래픽에서 무너집니다
- EBS 대역폭·IOPS — 동일한 함정. 사이즈 종속입니다
- 처리량과 CPU의 상관관계 — 스케일 병목이 CPU가 아니면(락 경합, DB 커넥션, 외부 API) CPU 기준 리사이징은 무의미합니다

Graviton 특성 하나 더: 코어당 피크 클럭은 x86 대비 낮은 편이지만 전 코어에서 일정하게 유지됩니다. 멀티스레드·스케일아웃 워크로드는 유리하고, 싱글스레드 바운드 워크로드(레거시 배치, 특정 DB 쿼리 플랜)는 주의 대상입니다. 이 구분을 진단 단계에서 태깅해두면 나중에 "왜 느려졌지" 소동을 막습니다.

4단계: 우선순위 매트릭스

두 축으로 4분면을 그립니다 — 월 절감 잠재액(Y) × 전환 난이도(X)

- 고액 / 저난이도 → 즉시 착수. 매니지드 서비스, stateless 컨테이너. 여기가 파일럿 대상
- 고액 / 고난이도 → 별도 프로젝트로 분리. 분기 로드맵
- 저액 / 저난이도 → 배치로 묶어서 일괄 처리
- 저액 / 고난이도 → 손대지 않음. 명시적으로 "안 함"으로 기록

여기에 보조 필터를 겹칩니다: 상태성(stateless 우선), SLO 엄격도, 롤백 용이성, SP 커버리지 상태(앞서 얘기한 EC2 Instance SP에 묶여 있으면 만기 시점까지 대기).

---

진단 산출물 형태

워크로드당 1행짜리 테이블이 최종 결과물입니다:

워크로드 | 현재타입/사이즈 | 월지출 | p99 CPU | 실사용메모리 | 네트워크피크
        | SP커버리지 | arm64판정 | 블로커 | 권고타입/사이즈 | 예상절감
        | 난이도 | 검증방법 | 분면

이 테이블 자체가 컨텐츠의 핵심 자산입니다. 나머지 편들은 전부 이 테이블의 특정 열을 어떻게 채우는지에 대한 설명이 됩니다.

---

컨텐츠에 꼭 넣을 함정 목록

1. 메모리 지표 없이 Compute Optimizer 권고 그대로 적용 → 가장 흔한 장애 원인
2. 평균 CPU로 판단 → 피크에서 터짐
3. 14일 룩백에 배치 주기 미포함 → 월말에 터짐
4. 네트워크·EBS 대역폭 무시 → CPU만 보고 다운사이징했다가 I/O에서 터짐
5. ASG 뒤 인스턴스를 개별로 진단 → ASG 단위(원하는 용량 + 인스턴스 타입 조합)로 봐야 함
6. vCPU 1:1 매핑 가정 → SMT 차이로 인한 과다 프로비저닝. 1편의 핵심 메시지와 연결
7. 개발/스테이징 제외 → 오히려 여기가 리사이징 여지가 훨씬 큽니다. Graviton 전환의 리스크 없는 연습장이기도 합니다

---

이 4단계를 그대로 진단 워크시트나 Athena 쿼리 세트로 만들어드릴 수 있습니다. CUR 스키마 기준으로 "arm64 가용 패밀리 × 과다 프로비저닝 × SP 미커버" 조합을 뽑는 쿼리부터 시작하면 3단계까지의 데이터가 대부분 자동으로 채워집니다. 만들어볼까요?

✻ Cooked for 1m 30s · done 오후 1:26

❯ 고난이도 , 저난이도를 어떻게 판별하는 거야?

난이도를 하나의 감(感)으로 매기면 사람마다 다르게 나와서 매트릭스가 무의미해집니다. 게이트 → 차원별 등급 → max 집계 순서로 기계적으로 판정하는 게 좋습니다.

---

0단계: 블로커 게이트 (점수 매기지 말고 걸러내기)

하나라도 해당되면 점수 계산 없이 즉시 High 또는 보류입니다.

- 상용 SW가 arm64 미지원 (EC2 위의 Oracle DB, 일부 상용 미들웨어)
- 라이선스가 아키텍처·코어 단위이고 재계약이 필요
- 필수 에이전트에 arm64 바이너리가 없음 (APM, EDR, 백업)
- 소스코드 접근 불가 또는 빌드 재현 불가한 인하우스 바이너리
- 커널 모듈·드라이버 의존
- 핫패스에 x86 인트린식(SSE/AVX)·인라인 어셈블리

이건 사용률과 무관하게 결정적입니다. 절감액이 크더라도 게이트를 못 넘으면 이번 분기 대상이 아닙니다.

---

1단계: 차원별 등급

차원 A — arm64 아티팩트 생산 비용

┌─────────┬────────────────────────────────────────────────────────────────────────────────────────────────────┐
│  등급   │                                                조건                                                │
├─────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ VeryLow │ 매니지드 서비스. 인스턴스 클래스 파라미터 변경만 (RDS, ElastiCache, OpenSearch, Lambda arm64 토글) │
├─────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Low     │ 인터프리터 언어 + 순수 라이브러리만. 재배포로 끝                                                   │
├─────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Low–Med │ JVM/.NET. 바이트코드는 이식되지만 JNI 라이브러리와 base image 확인 필요                            │
├─────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Medium  │ 컴파일 언어 + CI가 이미 멀티아치/크로스컴파일 지원 (Go·Rust는 target 추가 수준)                    │
├─────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ High    │ 컴파일 언어 + CI가 x86 단일 아키텍처. 빌더 인프라부터 구축해야 함                                  │
└─────────┴────────────────────────────────────────────────────────────────────────────────────────────────────┘

차원 B — 의존성 표면적 (개수로 정량화)

arm64 미지원 의존성 개수를 셉니다. "느낌"이 아니라 숫자입니다.

- 0개 → Low
- 1~2개, 모두 대체 가능 → Medium
- 3개 이상, 또는 1개라도 핵심 경로 → High

확인 방법: 컨테이너 이미지는 docker manifest inspect, OS 패키지는 서드파티 repo만 의심(AL2023·Ubuntu 기본 repo는 대부분 arm64 있음), 언어 패키지는 pin된 오래된 버전이 소스빌드로 떨어지는지 확인.

차원 C — 검증 비용 (대부분 빠뜨리는 차원, 실제 일정을 결정함)

┌────────┬─────────────────────────────────────────────────────────────────────────────────────┐
│  등급  │                                        조건                                         │
├────────┼─────────────────────────────────────────────────────────────────────────────────────┤
│ Low    │ stateless + 카나리 가능 + 자동 롤백 있음                                            │
├────────┼─────────────────────────────────────────────────────────────────────────────────────┤
│ Medium │ stateful이지만 replica promotion으로 전환 가능 (RDS 리더 승격, 캐시 워밍)           │
├────────┼─────────────────────────────────────────────────────────────────────────────────────┤
│ High   │ 엄격한 SLO(결제, p99 수 ms) → 정식 부하시험 필수 / 또는 성능 베이스라인이 아예 없음 │
└────────┴─────────────────────────────────────────────────────────────────────────────────────┘

베이스라인이 없는 경우가 특히 함정입니다. "느려졌는지" 판별할 기준이 없으면 전환 자체보다 측정 체계 구축이 더 오래 걸립니다.

차원 D — 조직적 요소

- 소유 팀이 명확한가, 오너 없는 레거시인가
- 배포 주기 — 주간 배포 팀 vs 연 2회 배포 시스템
- 변경관리 절차 — CAB 승인 필요 여부

기술적으로 Low여도 D가 High면 실제 리드타임은 몇 달이 됩니다.

2단계: 집계는 평균이 아니라 max

차원 중 가장 높은 등급이 그 워크로드의 등급입니다. 평균을 내면 안 됩니다 — 병목은 최악의 차원 하나이고, 나머지가 쉬운 것은 아무 도움이 되지 않기 때문입니다.

┌───────────┬───────────────┬────────────────────────────────┐
│ 최종 등급 │ 대략의 작업량 │           처리 방식            │
├───────────┼───────────────┼────────────────────────────────┤
│ VeryLow   │ 시간 단위     │ 변경관리 티켓 하나로 일괄 처리 │
├───────────┼───────────────┼────────────────────────────────┤
│ Low       │ 1~3 인일      │ 스프린트에 끼워넣기            │
├───────────┼───────────────┼────────────────────────────────┤
│ Medium    │ 1~3 인주      │ 스프린트 단위 과제             │
├───────────┼───────────────┼────────────────────────────────┤
│ High      │ 인월 단위     │ 별도 프로젝트, 분기 로드맵     │
└───────────┴───────────────┴────────────────────────────────┘

---

실전 팁: 분석하지 말고 한 대 띄워봐라

여기가 이 컨텐츠에서 가장 강하게 밀 메시지입니다.

위 체계는 우선순위를 세우기 위한 것이고, 실제 판정은 실험이 훨씬 정확합니다. t4g.medium 스팟 한 대는 시간당 몇 센트입니다. 30분 스모크 테스트가 2주짜리 문서 분석보다 확실합니다.

30분 판정 순서

1. 매니지드 서비스인가? → YES면 VeryLow, 끝
2. docker manifest inspect <image> — arm64 태그 있나?
3. 필수 에이전트 arm64 지원 — 벤더 문서 확인 (블로커 게이트)
4. Porting Advisor for Graviton 실행 → 리포트 심각도
5. arm64 인스턴스 1대에 실제로 배포해서 헬스체크 통과시켜보기
6. stateless인가, 카나리 가능한가?

5번을 통과하면 대부분의 추측이 사실로 바뀝니다. 실패하면 실패 로그가 곧 정확한 난이도 근거가 됩니다. 추정치보다 훨씬 설득력 있는 데이터고, 이 로그 자체가 컨텐츠의 좋은 소재이기도 합니다.

한 가지 주의: 스모크 테스트 통과는 기능 호환성만 증명합니다. 성능 회귀(싱글스레드 의존, LSE atomics 미적용으로 인한 락 경합)는 부하시험에서만 드러나므로, 차원 C의 등급은 스모크 테스트로 낮출 수 없습니다.

---

이 판정 체계를 체크리스트 형태의 스프레드시트나 스크립트로 만들어드릴 수 있습니다. 특히 2·3번(이미지 매니페스트 스캔 + 에이전트 인벤토리 대조)은 자동화가 잘 되는 영역이라, ECR 전체 이미지를 훑어서 arm64 준비도를 표로 뽑는 스크립트가 진단 초기 속도를 크게 올려줍니다.
