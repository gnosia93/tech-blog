핵심 앵글: "Graviton 전환 = 리사이징 기회"

가장 강력한 훅은 Graviton의 1 vCPU = 1 물리 코어(SMT 없음) 라는 점입니다. x86은 1 vCPU = 1 하이퍼스레드죠. 그래서 m5.4xlarge → m7g.4xlarge 같은 1:1 lift-and-shift는 대부분 과다 프로비저닝입니다. 실제로는 vCPU 수를 줄일 여지가 있고, 여기서 "전환 30% + 리사이징 20~30%"의 복리 절감이 나옵니다. 대부분의 Graviton 컨텐츠가 전환만 다루고 리사이징을 놓치기 때문에 차별점이 됩니다.

❯ ec2 인스턴스 sp 가 뭐야?

EC2 Instance Savings Plans

"특정 리전의 특정 인스턴스 패밀리를 1년 또는 3년간 시간당 $X씩 쓰겠다"고 약정하고 할인받는 요금 모델입니다. 예: us-east-1의 M5 패밀리에 시간당 $10 약정.

약정 단위가 인스턴스 개수가 아니라 시간당 금액($/hour) 이라는 점이 RI와 다릅니다. 약정액만큼은 할인가로 청구되고, 초과 사용분은 온디맨드 요금이 붙습니다.

유연한 것 / 고정된 것

바꿔도 계속 적용됨 (패밀리+리전 내에서)
- 인스턴스 사이즈 — m5.large ↔ m5.24xlarge
- OS — Linux ↔ Windows
- 테넌시, AZ

바꾸면 적용 안 됨
- 인스턴스 패밀리 — m5 → m6i도, m6i → m7g도 다른 패밀리로 취급
- 리전

3종 비교

┌─────────────────┬──────────────┬───────────────────────────────────────┬──────────────────────────┐
│                 │ 할인폭(최대) │                유연성                 │        커버 범위         │
├─────────────────┼──────────────┼───────────────────────────────────────┼──────────────────────────┤
│ EC2 Instance SP │ ~72%         │ 패밀리+리전 고정, 사이즈/OS만 유연    │ EC2만                    │
├─────────────────┼──────────────┼───────────────────────────────────────┼──────────────────────────┤
│ Compute SP      │ ~66%         │ 패밀리·리전·아키텍처 전부 자유        │ EC2 + Fargate + Lambda   │
├─────────────────┼──────────────┼───────────────────────────────────────┼──────────────────────────┤
│ Standard RI     │ ~72%         │ 패밀리+리전 고정 (조건부 사이즈 유연) │ EC2 (+ 일부 서비스별 RI) │
└─────────────────┴──────────────┴───────────────────────────────────────┴──────────────────────────┘

즉 EC2 Instance SP는 할인폭을 최대로 가져가는 대신 유연성을 포기하는 선택입니다. 여러 SP를 보유하면 AWS가 할인율 높은 쪽부터 자동 적용합니다.

Graviton 전환에서 문제가 되는 이유

앞서 언급한 "커밋 좌초"가 여기서 발생합니다. m6i 패밀리에 3년 EC2 Instance SP를 걸어둔 상태에서 m7g로 전환하면:

- Graviton 인스턴스는 온디맨드 요금으로 청구 (SP 적용 안 됨)
- 동시에 안 쓰는 m6i 약정액은 계속 청구

결과적으로 이중 지불이 되어, Graviton으로 30% 절감했다는 계산이 실제 청구서에서는 오히려 증가로 나타납니다.

대응 순서
1. 전환 대상 워크로드의 커버리지가 EC2 Instance SP인지 Compute SP인지 먼저 확인 (Cost Explorer의 Savings Plans 유틸리제이션/커버리지 리포트)
2. EC2 Instance SP라면 → 만기 시점에 맞춰 전환 일정 조정, 또는 만기 후 Compute SP로 갈아타기
3. 약정을 계단식으로(ladder) 쪼개서 갱신 → 아키텍처 전환 유연성 확보

Graviton 전환을 계획 중이라면 할인폭 6%p를 포기하고 Compute SP를 쓰는 게 대체로 유리합니다. 6%p 차이보다 전환으로 얻는 절감이 크기 때문입니다.

▎ 할인율 수치는 AWS 공식 기준의 "최대값"이고 인스턴스 타입·기간·선결제 옵션에 따라 실제값이 달라집니다. 컨텐츠에 넣을 때는 실제 대상 패밀리로 계산기 값을 뽑아 쓰는 걸 권합니다.

❯ 워크로드 진단에 대해서 좀더 자세히 설명해 줄래?

워크로드 진단은 두 개의 독립적인 축을 동시에 보는 작업입니다. 하나만 봐서는 판단이 안 됩니다.

- 축 A — arm64 호환성: 애초에 Graviton에서 돌아가는가? (기술적 가능성)
- 축 B — 리사이징 여지: 지금 과다 프로비저닝인가? (사용률)

arm64 준비가 됐어도 이미 딱 맞게 사이징된 워크로드가 있고, 과다 프로비저닝이지만 벤더 에이전트 때문에 arm64가 막힌 워크로드가 있습니다. 두 축을 곱해야 우선순위가 나옵니다.

2단계: 어떤 지표를 볼 것인가 (여기가 컨텐츠의 진짜 알맹이)

평균 CPU는 쓰지 마세요. 대신:

- p95/p99 CPU — 리사이징은 피크를 견디는지의 문제입니다
- 실사용 메모리(RSS 워킹셋) vs 할당 메모리 — JVM은 힙 설정 때문에 항상 꽉 차 보입니다. GC 로그나 힙 사용률을 따로 봐야 실제 여지가 보입니다
- 네트워크 대역폭·PPS — ⚠️ 가장 자주 빠뜨리는 항목. 인스턴스 baseline 대역폭은 사이즈에 비례합니다. c6i.8xlarge → c6i.2xlarge는 CPU에 여유가 있어도 네트워크에서 먼저 터집니다. 작은 사이즈는 burst 크레딧에 의존하므로 지속 트래픽에서 무너집니다
- EBS 대역폭·IOPS — 동일한 함정. 사이즈 종속입니다
- 처리량과 CPU의 상관관계 — 스케일 병목이 CPU가 아니면(락 경합, DB 커넥션, 외부 API) CPU 기준 리사이징은 무의미합니다

Graviton 특성 하나 더: 코어당 피크 클럭은 x86 대비 낮은 편이지만 전 코어에서 일정하게 유지됩니다. 멀티스레드·스케일아웃 워크로드는 유리하고, 싱글스레드 바운드 워크로드(레거시 배치, 특정 DB 쿼리 플랜)는 주의 대상입니다. 이 구분을 진단 단계에서 태깅해두면 나중에 "왜 느려졌지" 소동을 막습니다.

4단계: 우선순위 매트릭스

두 축으로 4분면을 그립니다 — 월 절감 잠재액(Y) × 전환 난이도(X)

- 고액 / 저난이도 → 즉시 착수. 매니지드 서비스, stateless 컨테이너. 여기가 파일럿 대상
- 고액 / 고난이도 → 별도 프로젝트로 분리. 분기 로드맵
- 저액 / 저난이도 → 배치로 묶어서 일괄 처리
- 저액 / 고난이도 → 손대지 않음. 명시적으로 "안 함"으로 기록

여기에 보조 필터를 겹칩니다: 상태성(stateless 우선), SLO 엄격도, 롤백 용이성, SP 커버리지 상태(앞서 얘기한 EC2 Instance SP에 묶여 있으면 만기 시점까지 대기).

진단 산출물 형태

워크로드당 1행짜리 테이블이 최종 결과물입니다:

워크로드 | 현재타입/사이즈 | 월지출 | p99 CPU | 실사용메모리 | 네트워크피크
        | SP커버리지 | arm64판정 | 블로커 | 권고타입/사이즈 | 예상절감
        | 난이도 | 검증방법 | 분면

이 테이블 자체가 컨텐츠의 핵심 자산입니다. 나머지 편들은 전부 이 테이블의 특정 열을 어떻게 채우는지에 대한 설명이 됩니다.

컨텐츠에 꼭 넣을 함정 목록

1. 메모리 지표 없이 Compute Optimizer 권고 그대로 적용 → 가장 흔한 장애 원인
2. 평균 CPU로 판단 → 피크에서 터짐
3. 14일 룩백에 배치 주기 미포함 → 월말에 터짐
4. 네트워크·EBS 대역폭 무시 → CPU만 보고 다운사이징했다가 I/O에서 터짐
5. ASG 뒤 인스턴스를 개별로 진단 → ASG 단위(원하는 용량 + 인스턴스 타입 조합)로 봐야 함
6. vCPU 1:1 매핑 가정 → SMT 차이로 인한 과다 프로비저닝. 1편의 핵심 메시지와 연결
7. 개발/스테이징 제외 → 오히려 여기가 리사이징 여지가 훨씬 큽니다. Graviton 전환의 리스크 없는 연습장이기도 합니다

---

이 4단계를 그대로 진단 워크시트나 Athena 쿼리 세트로 만들어드릴 수 있습니다. CUR 스키마 기준으로 "arm64 가용 패밀리 × 과다 프로비저닝 × SP 미커버" 조합을 뽑는 쿼리부터 시작하면 3단계까지의 데이터가 대부분 자동으로 채워집니다. 만들어볼까요?

0단계: 블로커 게이트 (점수 매기지 말고 걸러내기)

하나라도 해당되면 점수 계산 없이 즉시 High 또는 보류입니다.

- 상용 SW가 arm64 미지원 (EC2 위의 Oracle DB, 일부 상용 미들웨어)
- 라이선스가 아키텍처·코어 단위이고 재계약이 필요
- 필수 에이전트에 arm64 바이너리가 없음 (APM, EDR, 백업)
- 소스코드 접근 불가 또는 빌드 재현 불가한 인하우스 바이너리
- 커널 모듈·드라이버 의존
- 핫패스에 x86 인트린식(SSE/AVX)·인라인 어셈블리

이건 사용률과 무관하게 결정적입니다. 절감액이 크더라도 게이트를 못 넘으면 이번 분기 대상이 아닙니다.

차원 B — 의존성 표면적 (개수로 정량화)

arm64 미지원 의존성 개수를 셉니다. "느낌"이 아니라 숫자입니다.

- 0개 → Low
- 1~2개, 모두 대체 가능 → Medium
- 3개 이상, 또는 1개라도 핵심 경로 → High

확인 방법: 컨테이너 이미지는 docker manifest inspect, OS 패키지는 서드파티 repo만 의심(AL2023·Ubuntu 기본 repo는 대부분 arm64 있음), 언어 패키지는 pin된 오래된 버전이 소스빌드로 떨어지는지 확인.

실전 팁: 분석하지 말고 한 대 띄워봐라

여기가 이 컨텐츠에서 가장 강하게 밀 메시지입니다.

위 체계는 우선순위를 세우기 위한 것이고, 실제 판정은 실험이 훨씬 정확합니다. t4g.medium 스팟 한 대는 시간당 몇 센트입니다. 30분 스모크 테스트가 2주짜리 문서 분석보다 확실합니다.

30분 판정 순서

1. 매니지드 서비스인가? → YES면 VeryLow, 끝
2. docker manifest inspect <image> — arm64 태그 있나?
3. 필수 에이전트 arm64 지원 — 벤더 문서 확인 (블로커 게이트)
4. Porting Advisor for Graviton 실행 → 리포트 심각도
5. arm64 인스턴스 1대에 실제로 배포해서 헬스체크 통과시켜보기
6. stateless인가, 카나리 가능한가?

5번을 통과하면 대부분의 추측이 사실로 바뀝니다. 실패하면 실패 로그가 곧 정확한 난이도 근거가 됩니다. 추정치보다 훨씬 설득력 있는 데이터고, 이 로그 자체가 컨텐츠의 좋은 소재이기도 합니다.

한 가지 주의: 스모크 테스트 통과는 기능 호환성만 증명합니다. 성능 회귀(싱글스레드 의존, LSE atomics 미적용으로 인한 락 경합)는 부하시험에서만 드러나므로, 차원 C의 등급은 스모크 테스트로 낮출 수 없습니다.

이 판정 체계를 체크리스트 형태의 스프레드시트나 스크립트로 만들어드릴 수 있습니다. 특히 2·3번(이미지 매니페스트 스캔 + 에이전트 인벤토리 대조)은 자동화가 잘 되는 영역이라, ECR 전체 이미지를 훑어서 arm64 준비도를 표로 뽑는 스크립트가 진단 초기 속도를 크게 올려줍니다.


 비용절감이 목표인 상태에서 세대를 건너띄게 되면.. 비용이 더 나오잖아. 그럼 인스턴스 콘솔리데이터션을 해야 하는데. 이건 너무 어렵지 않아?

정확한 지적이고, 제 앞 답변의 "최신 Graviton으로 가라"는 부분을 정정해야 합니다.

Graviton은 세대가 올라갈수록 시간당 단가가 비쌉니다

us-east-1 기준 대략 (검증 필요):

┌────────────────────────┬─────────┐
│        인스턴스        │ 시간당  │
├────────────────────────┼─────────┤
│ m5.xlarge / m6i.xlarge │ ~$0.192 │
├────────────────────────┼─────────┤
│ m6g.xlarge             │ ~$0.154 │
├────────────────────────┼─────────┤
│ m7g.xlarge             │ ~$0.163 │
├────────────────────────┼─────────┤
│ m8g.xlarge             │ ~$0.180 │
└────────────────────────┴─────────┘

세대가 올라가며 개선되는 건 가격대비성능이지 시간당 단가가 아닙니다. m8g는 m7g보다 성능이 좋지만 단가도 높습니다.

그래서 같은 사이즈로 최신 세대에 매핑하면, 늘어난 성능은 유휴로 놀고 단가만 더 냅니다. m6g로 갔으면 20% 절감인데 m8g로 가면 6% 절감이 되는 식이죠. 님이 말한 그대로입니다.

즉 최신 세대의 이점은 콘솔리데이션(대수 축소 또는 사이즈 축소)을 통해서만 실현됩니다. 콘솔리데이션이 최신 세대의 전제조건입니다.

그런데 콘솔리데이션의 난이도는 워크로드가 아니라 운영 모델에 달려 있습니다

이미 자동인 곳 — 여기선 별도 작업이 사실상 없습니다:

- ASG + 타겟 트래킹 정책 — CPU 50% 목표로 걸어뒀다면, 성능이 좋아지는 순간 ASG가 알아서 대수를 줄입니다. "콘솔리데이션"이라는 프로젝트가 필요 없고, 기존 메커니즘이 대신 해줍니다
- Karpenter — consolidationPolicy: WhenEmptyOrUnderutilized가 그 기능 자체입니다. Pod requests를 그대로 두면 더 적은/작은 노드로 재배치됩니다
- Lambda / Fargate — 인스턴스 개념이 없고 사용량 과금이라 성능 향상이 곧바로 비용 감소로 이어집니다. arm64 토글이 사실상 끝

진짜 어려운 곳:

- 스케일링 정책 없이 고정 대수로 도는 pet 인스턴스
- Stateful 싱글톤 (DB primary, 브로커)
- 대수가 쿼럼에 묶인 것 — Kafka, ZooKeeper, etcd, OpenSearch (홀수 노드 제약, 파티션 재분배)
- 라이선스가 노드 수 기준인 것
- 수평 스케일이 안 되는 앱

그래서 의사결정 규칙이 뒤집힙니다

┌────────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
│             운영 모델              │                                    전략                                     │
├────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
│ ASG·Karpenter·Fargate 위 stateless │ 최신 세대(m8g)로. 콘솔리데이션이 자동으로 일어나므로 성능을 그대로 회수     │
├────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
│ 고정 대수 pet 인스턴스             │ 가장 저렴한 Graviton(m6g/m7g)으로. 사이즈 유지. 콘솔리데이션 시도하지 말 것 │
├────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
│ Stateful·쿼럼                      │ 저렴한 세대 + 사이즈 유지. 작은 절감폭 받고 넘어감                          │
├────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
│ 매니지드(RDS 등)                   │ 대수가 아니라 사이즈 문제. 클래스 한 단계 내리기를 별도 검토                │
└────────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘

핵심 재프레이밍

콘솔리데이션은 절감의 전제조건이 아닙니다. 최신 세대를 정당화하는 조건일 뿐입니다.

콘솔리데이션이 어려운 워크로드는 애초에 최신 세대로 가지 않으면 됩니다. m5.xlarge → m6g.xlarge 같은 사이즈 매핑만으로도 20% 정도 절감되고, 여기엔 콘솔리데이션이 전혀 필요 없습니다. 어려운 일을 안 해도 상당한 절감이 나온다는 뜻입니다.

그리고 고정 대수 인스턴스라도 일회성 사이즈 축소는 대수 축소보다 훨씬 쉽습니다. m6g.2xlarge → m6g.xlarge는 stop/start면 끝이니까요. 다만 메모리가 반으로 줄어드는 제약이 걸리므로, 메모리 여유가 있는 경우에만 가능합니다.

컨텐츠 관점

이게 앞서 얘기한 것보다 훨씬 좋은 1편 주제입니다. 대부분의 Graviton 자료가 "최신 세대가 가격대비성능 최고"라고만 말하고 단가는 더 비싸다는 사실을 건너뜁니다. 그래서 같은 사이즈로 m8g에 옮긴 팀은 청구서를 보고 당황하게 되죠.

▎ "최신 Graviton이 항상 정답은 아니다 — 콘솔리데이션할 수 없다면 구세대가 낫다"

여기에 세대별 단가 표 한 장 + 위 의사결정 규칙 표를 붙이면, 흔한 오해를 정면으로 교정하는 강한 컨텐츠가 됩니다.

▎ 위 가격은 기억에 기반한 근사치이고 리전·시점에 따라 다릅니다. 컨텐츠에 넣기 전에 실제 대상 리전의 가격표로 재확인이 필요합니다. 원하시면 AWS Pricing API로 세대별 단가 비교표를 뽑는 스크립트를 만들어드리겠습니다.

│ 방향      │ 수직 (vertical)                               │ 수평 (horizontal)           │
├───────────┼───────────────────────────────────────────────┼─────────────────────────────┤
│ 조정 대상 │ 리소스 하나의 크기                            │ 리소스의 개수               │
├───────────┼───────────────────────────────────────────────┼─────────────────────────────┤
│ 예시      │ m6g.2xlarge → m6g.xlarge<br>m → c 패밀리 변경 │ 10대 → 6대                  │
├───────────┼───────────────────────────────────────────────┼─────────────────────────────┤
│ 전제      │ 개별 인스턴스에 여유가 있음                   │ 워크로드를 재배치할 수 있음 │
└───────────┴───────────────────────────────────────────────┴─────────────────────────────┘

총 비용 = 개수 × 단가(크기에 비례) 이므로 두 축 모두 곱셈에 들어갑니다. 서로 독립적이고, 둘 다 하면 곱해집니다.

방향이 반대일 수도 있습니다

이게 둘이 다른 개념이라는 가장 명확한 증거입니다. 콘솔리데이션 중에 빈 패킹이 있는데:

10 × m6g.large  (총 20 vCPU)  →  3 × m6g.2xlarge  (총 24 vCPU)

인스턴스 개수는 줄었지만 개별 사이즈는 커졌습니다. 오버헤드(OS, 에이전트, 예약 용량)가 대수만큼 곱해지던 걸 줄이는 효과죠. 라이트 사이징 관점에서는 "업사이징"인데 콘솔리데이션 관점에서는 성공입니다.

혼동이 생기는 이유

1. 결과적으로 둘 다 총 용량을 줄입니다 — 청구서에서는 구분이 안 됩니다
2. 운영 모델이 어느 축을 쓸지 강제합니다. ASG 위에서는 사이즈 고정하고 대수를 줄이는 게 자연스럽고, 고정 대수 pet 인스턴스에서는 대수 고정하고 사이즈를 줄이는 게 유일한 방법입니다. 한 환경에서는 한 축만 쓰게 되니 같은 것처럼 보입니다
3. Karpenter의 consolidation 기능이 실제로 둘 다 합니다 — 노드를 없애기도 하고 더 작은 노드로 교체하기도 합니다. 도구 이름 때문에 용어가 섞입니다
4. AWS 용어도 엄격하지 않습니다 — Cost Explorer의 "Rightsizing recommendations"에는 타입 변경 권고와 종료(terminate) 권고가 같이 들어 있는데, 종료는 사실 콘솔리데이션에 가깝습니다

Graviton 맥락에서의 정리

앞서 제가 "콘솔리데이션(대수 축소 또는 사이즈 축소)"이라고 묶어 쓴 건 부정확했습니다. 정확히는 이렇습니다:

Graviton 전환으로 얻는 것은 성능 여유(headroom) 입니다. 이걸 비용으로 바꾸는 경로가 두 개:

- 라이트 사이징 — 인스턴스를 더 작게
- 콘솔리데이션 — 인스턴스를 더 적게

그리고 어느 경로가 열려 있는지를 운영 모델이 결정합니다. ASG·Karpenter 위 stateless는 콘솔리데이션 경로가 자동으로 열려 있고, 고정 대수 pet 인스턴스는 라이트 사이징 경로만 있습니다(메모리 제약에 걸리기 쉬움). 쿼럼에 묶인 워크로드는 둘 다 막혀 있어서 여유를 회수할 방법이 없습니다.

앞서 만든 의사결정 표의 논리가 바로 이것이었습니다.

컨텐츠 관점

레포 이름이 right-sizing인데 실제 절감의 상당 부분이 콘솔리데이션에서 나온다면, 1편 앞부분에서 두 용어를 명시적으로 구분하고 시작하는 게 좋습니다. 독자와 이해관계자가 계속 섞어 쓸 용어이기 때문입니다.

▎ "Graviton 여유를 비용으로 바꾸는 두 가지 방법: 작게 만들기(라이트 사이징) vs 적게 만들기(콘솔리데이션). 당신의 운영 모델이 어느 쪽이 가능한지 이미 결정해뒀다."

이 한 문장이 시리즈 전체의 프레임이 될 수 있습니다.

❯ 라이트 사이징 하는 방법이 뭐야?

라이트 사이징은 인스턴스 그리드 위에서 목표점을 찾는 작업입니다. 이 그리드를 이해하면 방법이 자연스럽게 나옵니다.

전제: 인스턴스는 2차원 격자다

- 패밀리 축 = 메모리:vCPU 비율 — c=2GB, m=4GB, r=8GB, x=16GB (vCPU당)
- 사이즈 축 = 배수 — large(2vCPU) → xlarge(4) → 2xlarge(8) → 4xlarge(16) …

핵심은 사이즈만 내리면 vCPU와 메모리가 함께 반토막이라는 점입니다. 그래서 "CPU는 남는데 메모리는 딱 맞는" 가장 흔한 상황에서는 사이즈를 못 내립니다. 이때 필요한 건 패밀리 이동입니다. 라이트 사이징이 단순히 "한 단계 내리기"가 아닌 이유죠.

---

절차

1단계 — 필요량을 숫자로 확정

필요 vCPU = 현재 vCPU × (피크 CPU 사용률 ÷ 목표 사용률)

목표 사용률(헤드룸)을 먼저 정해야 합니다. ASG 뒤 stateless면 65~70%, 단일 인스턴스면 50% 정도로 여유를 크게 둡니다.

필요 메모리 = 피크 워킹셋 × 1.2~1.3 + OS·에이전트 오버헤드(1~2GB)

JVM은 힙 설정값이 아니라 실사용 힙 + 비힙(metaspace, 스레드 스택, direct buffer)을 봐야 합니다. 힙 설정만 보면 항상 꽉 차 보여서 리사이징 여지가 안 보입니다.

2단계 — 그리드에서 후보 선정

필요메모리 ÷ 필요vCPU 로 요구 비율을 계산하고, 그 비율에 맞는 패밀리를 고릅니다.

┌───────────┬───────────────────────┐
│ 요구 비율 │        패밀리         │
├───────────┼───────────────────────┤
│ ≤ 2       │ c                     │
├───────────┼───────────────────────┤
│ 2~4       │ m                     │
├───────────┼───────────────────────┤
│ 4~8       │ r                     │
├───────────┼───────────────────────┤
│ > 8       │ x, 또는 r + 사이즈 업 │
└───────────┴───────────────────────┘

그 패밀리에서 vCPU·메모리 두 조건을 모두 만족하는 최소 사이즈가 후보입니다.

3단계 — 제약 조건 검증 (여기서 후보가 탈락합니다)

사이즈를 내리면 CPU·메모리만 줄지 않습니다:

- 네트워크 baseline 대역폭 — 사이즈 비례. "Up to 12.5 Gbps"의 baseline이 실제로 얼마인지 확인. 작은 사이즈는 burst 크레딧 의존이라 지속 트래픽에서 무너집니다
- EBS 대역폭·IOPS — 동일하게 사이즈 종속
- ENI·IP 개수 — ⚠️ EKS에서 중요. VPC CNI는 ENI당 IP 수로 노드당 Pod 수가 제한되므로, 사이즈를 내리면 Pod 밀도 상한이 떨어집니다
- 로컬 NVMe — d/gd 변종 여부와 용량

탈락하면 한 사이즈 위로 되돌립니다.

4단계 — 검증

- 부하시험: 피크 재현 후 p99 레이턴시 비교. SLO 엄격한 워크로드는 필수
- 카나리: 소수 인스턴스만 교체하고 지표 대조. stateless면 이게 가장 빠름
- 관찰 기간: 최소 1 비즈니스 사이클 — 주간 패턴 + 월말 배치를 포함해야 합니다

5단계 — 적용

┌──────────┬────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
│   대상   │                    방법                    │                          주의                           │
├──────────┼────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
│ EC2 단독 │ stop → 타입 변경 → start                   │ 퍼블릭 IP 변경(EIP 없으면), 인스턴스 스토어 데이터 소실 │
├──────────┼────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
│ ASG      │ Launch Template 새 버전 → instance refresh │ 점진 교체 비율 설정                                     │
├──────────┼────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
│ RDS      │ 인스턴스 클래스 수정                       │ Multi-AZ면 failover로 다운타임 최소화                   │
├──────────┼────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
│ 컨테이너 │ Pod requests / task definition 변경        │ 아래 참조                                               │
└──────────┴────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘

6단계 — 롤백 기준을 미리 숫자로

"p99가 N ms 초과", "에러율 N% 초과", "CPU N% 초과" — 적용 전에 정해두지 않으면 지표가 흔들릴 때 판단이 감정적으로 흐릅니다.

---

예시

m6i.2xlarge (8 vCPU / 32GB), p99 CPU 25%, 실사용 메모리 12GB

필요 vCPU   = 8 × (0.25 / 0.60) = 3.3  →  4
필요 메모리 = 12 × 1.3 + 1.5     = 17GB
요구 비율   = 17 / 4 = 4.25       →  r 패밀리

- m7g.xlarge (4/16) → 메모리 17GB 요구를 못 맞춤. 탈락
- r7g.xlarge (4/32) → 조건 충족. 메모리는 다소 과잉

결과: m6i.2xlarge → r7g.xlarge. vCPU는 절반, 메모리는 동일, 단가는 대략 40%대 하락(리전·시점 확인 필요).

여기서 m → r로 패밀리를 옮긴 게 핵심입니다. 같은 패밀리에서 사이즈만 내렸다면 메모리 때문에 아예 못 내렸을 케이스입니다.

---

컨테이너 환경은 대상이 다릅니다

EKS·ECS에서 라이트 사이징의 대상은 인스턴스가 아니라 Pod/Task의 requests입니다. 노드 사이즈는 Karpenter가 requests에 맞춰 자동으로 고르므로, requests가 과대하면 노드를 어떻게 만져도 절감이 안 됩니다.

- VPA를 recommendation 모드로 돌려서 권고값 수집 (자동 적용은 하지 말 것)
- Goldilocks 로 네임스페이스별 권고 시각화
- Compute Optimizer도 ECS on Fargate 권고를 제공

많은 팀이 노드 타입만 만지작거리다 절감이 안 나오는데, 원인은 대개 requests입니다.

---

흔한 실수

1. 평균 CPU 기준 판정 → 피크에서 터짐
2. 메모리 버퍼 없이 딱 맞게 → OOM
3. 네트워크·EBS·ENI 제약 무시 → CPU 여유만 보고 내렸다가 I/O나 Pod 밀도에서 막힘
4. 한 번에 두 단계 내리기 → 한 단계씩, 매번 관찰
5. 헤드룸 목표를 정하지 않음 → 판단 기준이 없어 논쟁만 길어짐
6. 개발·스테이징 제외 → 정작 여기가 여지가 가장 큼

---

1단계·2단계는 계산이 정해져 있어서 자동화가 잘 됩니다. CloudWatch에서 p99 CPU와 메모리를 긁어와 요구 비율을 계산하고, 인스턴스 카탈로그에서 후보를 추천하는 스크립트를 만들면 진단 결과가 바로 권고안으로 이어집니다. 필요하시면 만들어드리겠습니다.
